## 1. Почему базовый замер отклонён

Отчёт по Match-3: 7168 кадров за 62.1 с при raster p50 = 33.54 мс.

```
7168 / 62.1 с        = 115.4 fps → интервал 8.66 мс
raster p50 33.54 мс  →  29.8 fps
```

Кадр не может выходить каждые 8.66 мс, если его одна только растеризация
занимает 33.54 мс. Максимум кадров при таком растре за 62.1 с — 1851.
Расхождение **в 3.9 раза**. То же по Classic: 3046 кадров за 63.4 с (48 fps)
при raster p50 7.37 мс, который позволял бы более 100 fps.

Причина, судя по коду: в панели рядом стоят **накопительный** счётчик
`totalRecordedFrames` и перцентили, посчитанные по **окну** буфера. Это
разные выборки, и подпись этого не говорит. Их сопоставление и даёт
невозможную пару.

## 2. Перемеренная база

Метод: сброс счётчика → навигация в режим → выдержка → возврат → снятие.
Окно замерено по стенным часам. Устройство 2209116AG, релизный билд с
`ENABLE_DIAGNOSTICS=true`, дисплей в режиме 120 Гц.

| Режим | Кадров | Окно | Факт. fps | Build p50/p90/p99 | Raster p50/p90/p99 | Согласованность |
| --- | --- | --- | --- | --- | --- | --- |
| Match-3, простой | 956 | ~36 с | **26.6** | 7.76 / 11.89 / 18.38 | **38.94** / 39.51 / 41.25 | 1000/38.94 = 25.7 fps ✔ |
| Classic, пустая доска | 820 | ~26 с | **31.5** | 2.00 / 3.06 / 6.50 | **32.01** / 32.49 / 33.41 | 1000/32.01 = 31.2 fps ✔ |

Обе строки сходятся сами с собой: наблюдаемый fps совпадает с обратной
величиной растра. Это и есть признак исправного замера.

**Реальное положение: приложение рисует 26-31 fps на 120-герцовом экране.**
Вывод отчёта «Classic Mode держит уверенные 60 fps» неверен дважды: и по
величине, и по цели — бюджет кадра на этом дисплее 8.33 мс, а не 16.67.

## 3. Три правки к инструменту

**3.1. Порог jank прибит к 60 Гц.**
`jankThresholdMicroseconds = 16667` — константа. Тестовое устройство работает
на 120 Гц (`mActiveSfDisplayMode: refreshRate=120.00001`), бюджет 8.33 мс.
Инструмент **занижает** jank ровно на том устройстве, на котором снималась
база. Порог надо брать из `PlatformDispatcher.views.first.display.refreshRate`.

**3.2. Панель показывает две разные выборки как одну.**
`956 / 3600 (total: 956)` и перцентили ниже — это окно буфера и накопительный
счётчик. Подписать явно, что перцентили считаются по последним N кадрам.

**3.3. Не хватает одного числа, которое делает отчёт самопроверяемым.**
Если бы панель показывала **fps за окно замера**, противоречие было бы видно
сразу, без арифметики на стороне. Нужен таймстамп начала окна и
`frames / elapsed`. Это самая дешёвая правка из трёх и самая ценная.

## 4. Что база на самом деле нашла

Инструмент своё дело сделал: он вскрыл проблему, которой никто не подозревал.

**Ведущая гипотеза: полноэкранный фон перерисовывается каждый кадр.**

Доказательство — косвенное, но сильное: **32 мс растра на пустой доске
Classic**, где нет ни одной стеклянной фигуры, ни каскада, ни частиц. Три
структурно разных экрана дают почти одинаковый растр. Значит стоимость общая,
а не в содержимом.

`NebulaBackground` стоит во всех трёх экранах через `Positioned.fill` и
**нигде не обёрнут в `RepaintBoundary`**. Его `shouldRepaint => false`
предотвращает лишние вызовы `paint()`, только когда грязен сам виджет; он не
выделяет его в отдельный слой. `GameWidget` пачкает дерево каждый кадр, и
девять полноэкранных градиентных проходов (восемь туманности плюс виньетка)
переписываются и перерастеризуются на 1080x2400 шестьдесят-сто раз в секунду.

Виньетка — девятый проход — добавлена мной в визуальной сессии. Если гипотеза
верна, я же её и ухудшил.

**Эксперимент для подтверждения:** обернуть `NebulaBackground` в
`RepaintBoundary` и перемерить те же два режима тем же методом. Правка в две
строки. Если растр падает — причина найдена; если нет — гипотеза снята и
ищем дальше, уже с исправным инструментом.

именно затем, чтобы не украшать игру, идущую на 26 fps. Если фон действительно
стоит 32 мс, то это бюджет, за который окупятся все ударные волны разом.
