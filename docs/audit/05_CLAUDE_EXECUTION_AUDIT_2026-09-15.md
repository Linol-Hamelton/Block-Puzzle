# Аудит работы Claude и приоритетов развития

Дата: 2026-09-15. Автор: Codex. Контрольная точка: `eb47a89`.
Статус: независимый аудит; предложения ниже не являются новыми решениями DEC.

## Вывод

Claude существенно продвинул проект: свёл ветки и планы, интегрировал три
режима, исправил несколько ошибок production-конфигурации, поднял Android/Firebase
и начал проверку на телефоне. Это полезная инженерная работа. Однако завершённость
этапа A переоценена: проверенные компоненты пока не образуют проверенный сценарий.
Самый показательный пример — 16 зелёных тестов Firestore при отклонении настоящего
JSON приложения. Переход «остался Blaze, затем B» преждевременен.

Главный вектор сейчас — довести существующие три режима до воспроизводимой
Android-сборки с надёжным сохранением, наблюдаемыми событиями и одним завершённым
коммерческим сценарием. Новые режимы и расширение генеративного инструментария
имеют меньшую ожидаемую отдачу, пока эти цепочки не работают.

## Приоритетные дефекты

P1 здесь означает препятствие надёжному релизу или приёмке соответствующего
этапа. P2 — значимый риск конфигурации, воспроизводимости или процесса.

### F1 — P1: правила Firestore отвергают реальное сохранение

**Новая несовместимость при подключении правил к существующему клиенту.**
[Клиент](../../apps/mobile/lib/data/progression/cloud_player_progress_repository.dart)
пишет `users/{uid}` как `{progress: state.toJson(), lastSyncUtc: ...}`.
[Правила](../../firestore.rules) разрешают только плоские camelCase-поля
`schemaVersion`, `bestScore`, `settings` и другие. Настоящая модель внутри
`progress` использует snake_case, включая `schema_version` и `best_score`.

В эмулятор передан JSON, полученный непосредственно через
`PlayerProgressState.initialForDay(...).toJson()`. Запись владельцем с `merge:true`
отклонена. Локальное сохранение при этом успешно, а `_saveToCloud` подавляет ошибку.
Пользователь может обнаружить отсутствие облачной копии лишь после потери устройства.

Существующие тесты проходят потому, что `validProgress` в
[rules.test.js](../../infra/firestore_rules_tests/rules.test.js) описывает другую схему.
Ещё две проверки подтвердили: разрешённые имена принимают неверные типы и
отрицательный score; наличие серверного `entitlements` в документе блокирует
обычное клиентское merge-обновление, поскольку `hasOnly` проверяет итоговый документ.
Последнее — воспроизведение предусмотренного комментариями сценария, не утверждение,
что сервер уже создаёт такие документы в production.

**Исправление и приёмка:** единый контракт клиент/правила/фикстуры, проверки типов,
разделение клиентского прогресса и серверных прав покупки. Нельзя просто разрешить
произвольный `progress`: модель содержит `economy_state.owned_product_ids` и
`cosmetics_state`. Проверить владельца, постороннего, гостя, merge и запрещённые
права на реальном сериализованном payload; затем save → новая установка → load.
Точную опубликованную версию rules Codex отдельно из облака не выгружал.

### F2 — P1: Android CI не получает обязательную Firebase-конфигурацию

**Новая сборочная зависимость не доведена до CI.**
В [build.gradle](../../apps/mobile/android/app/build.gradle) безусловно применяется
`com.google.gms.google-services`. `google-services.json` исключён из Git и есть
локально, но ни [mobile-ci.yml](../../.github/workflows/mobile-ci.yml), ни
[android-release.yml](../../.github/workflows/android-release.yml) не создают его.
Второй workflow декодирует только keystore. На чистом runner файл отсутствует,
а Gradle-задача обработки Google Services его требует. Проверка статическая;
отдельный чистый GitHub runner в рамках аудита не запускался.

**Приёмка:** обеспечить конфигурацию до Gradle-сборки выбранным проектным способом;
собрать APK/AAB из чистого checkout. Добавить rules-тесты в CI: текущие workflows
их не запускают и не реагируют на изменения `firestore.rules`/`infra`.
Явные Dart `FirebaseOptions` не заменяют входной файл Gradle-плагина.

### F3 — P1: опубликованные выключатели режимов не выключают режимы

**Незакрытый A7 / DEC-0002.** В Firebase есть `feature_classic_enabled`,
`feature_tetris_enabled`, `feature_match3_enabled`, но в клиентском коде нет их
потребителей. [HomeScreen](../../apps/mobile/lib/ui/screens/home_screen.dart)
безусловно открывает все три экрана. Поиск имён флагов находит только комментарий
в преобразователе ключей. Наличие параметров на сервере не даёт операционного контроля.

**Приёмка:** флаг запрещает вход из меню и прямой навигацией; политика для уже
идущего раунда задана явно. Проверить каждый режим на устройстве, включая перезапуск
и offline. У известных mode-флагов должны быть явные типизированные defaults.

### F4 — P1: кеш Remote Config после перезапуска не используется при сбое fetch

**Незакрытый критерий A3, а не новая ошибка merge.**
[Репозиторий](../../apps/mobile/lib/data/remote_config/firebase_remote_config_repository.dart)
держит только `_inMemorySnapshot`. Чтение `getAll()` стоит после успешного
`fetchAndActivate()`. При исключении после перезапуска возвращаются bundled defaults;
ранее активированный Firebase-кеш отдельно не читается.

**Приёмка:** загрузить ранее активированные значения SDK до сетевой попытки,
корректно совместить их с defaults; проверить restart/offline, плохие типы и
частичный ответ. Восемь тестов key map не проверяют репозиторий, merge или этот отказ.

### F5 — P1: release и Web объявлены проверенными шире, чем позволяют доказательства

[mobile-ci.yml](../../.github/workflows/mobile-ci.yml) по-прежнему собирает
`flutter build web --release` без APP_ENV/APP_FLAVOR. В таком runtime защитная
проверка `kReleaseMode && useDebugAdapters` выбрасывает ошибку до `runApp`.
Дополнительно [firebase_options.dart](../../apps/mobile/lib/firebase_options.dart)
настроен только для Android и бросает `UnsupportedError` для Web и остальных
платформ. В debug bootstrap повторно бросает ошибку; старый Web-путь не сохранён.
Успех компиляции bundle не проверяет его запуск.

`eb47a89` сообщает о profile-сборке на Redmi: prod, flavor release, debug adapters
no, Analytics upload 204 и отправке Crashlytics. Это существенно сильнее чтения
исходников. Однако profile не является release-бинарником; панель показывает
`AppConfig.useDebugAdapters`, а не тип каждого разрешённого DI-сервиса.

**Приёмка:** определить поддерживаемые цели CI; исправить запуск оставшихся целей.
На release APK проверить фактические Analytics/CrashReporter/RemoteConfig/IAP
адаптеры и их операции. Проверить native fatal/ANR и символы отдельно: нынешняя
кнопка правильно обозначена как non-fatal и эти пути не покрывает.

### F6 — P1 этапа B: restore меняет последовательность игры

**Известный долг нового режима, уже предусмотренный B1.**
[Tetris](../../apps/mobile/lib/domain/tetris/tetris_engine.dart) не сохраняет bag/RNG,
[Match-3](../../apps/mobile/lib/domain/match3/match3_engine.dart) — состояние spawner.
Независимый probe реальных классов, seed 42:

- Tetris: очередь `[l,t,j,s,i]` после restore становится `[o,l,t,j,s]`.
- Match-3: один и тот же допустимый swap `(3,2) → (4,2)` даёт разные итоговые доски
  у оригинального движка и восстановленного из его snapshot.

**Приёмка:** сериализовать состояние генератора/очереди, версионировать snapshot,
проверить одинаковую последовательность следующих действий до/после восстановления.
Затем проверить process death, а не только паузу; сохранить идентичность и время раунда.

### F7 — P2: часть dart-defines теряется в AOT

**Унаследованный дефект, существенный для заявления о закрытии A0.**
[AppConfig](../../apps/mobile/lib/core/config/app_config.dart) читает APP_FLAVOR и
необязательные API URL через неконстантный `String.fromEnvironment(key)`.
Проверен реальный класс: при одинаковых `APP_ENV=prod`, `APP_FLAVOR=stage`,
`CONFIG_API_BASE_URL=https://example.invalid` Dart JIT возвращает `stage` и URL,
скомпилированный exe — `release` и `null`.

Обычный prod/release продолжает совпадать с fallback, поэтому неверно утверждать,
что все релизные сборки получают debug-адаптеры. Ошибка проявляется на явных
переопределениях. **Приёмка:** const-чтение каждого литерального ключа и проверка AOT.

## Остальные существенные незавершённые обязательства

1. **Коммерция (A5/C).** `verifyPurchase` не задаёт runtime `serviceAccount` явно.
   Правильная привязка purchase token → UID в транзакции сохранена. Blaze и доступ
   Play — внешние зависимости, но подготовка principal/контракта/тестов доступна
   локально. OAuth entries в Firebase не означают реализованный Google Sign-In:
   в приложении нет account linking перед `purchaseProduct`. Это необходимо для
   сценария покупки и восстановления после переустановки согласно DEC-0018.
2. **Cosmetics-only (DEC-0008).** В опубликованном RC
   `iap_rewarded_tools_unlimited_enabled=true`; клиентский каталог содержит
   `utility_tools_pass`. Это унаследованная функциональность, которую текущая
   публикация конфигурации оставляет активной вопреки принятому ограничению.
   Проверить весь доступный каталог и fallback, оставить утверждённый сценарий.
3. **Измерения.** Собственный `session_start` привязан к Classic-контроллеру;
   Classic `game_start/game_end` не несут `game_id`, в отличие от новых режимов.
   `_beginRound` Tetris/Match-3 при restore создаёт новый round ID и время начала.
   Автоматические сессии Firebase существуют отдельно и не исправляют согласованность
   проектной схемы. До сравнений retention нужны одинаковые события трёх режимов.
4. **Жизненный цикл (B3/B4).** GameLoopController — factory, но изменяемые
   ABExperiment/Onboarding/Progression-сервисы остаются lazy singleton. DEC-0016
   ещё не реализован. Нужны scoped lifetime и проверки повторного входа/выхода.
5. **UI (B5).** `test/widget_test.dart` содержит `expect(true, isTrue)`.
   214 тестов не доказывают клики, навигацию, восстановление экрана и покупки.
   Нужен небольшой набор сквозных пользовательских сценариев вместо роста счётчика.
6. **Диагностика/analytics.** `firebase_ready` и ряд игровых параметров передаются
   как bool. Установленный firebase_analytics 11.6.0 в Dart assert допускает String/num.
   Это риск debug-проверок production-адаптера; поведение native release этим аудитом
   не объявляется сломанным. Нормализовать контракт событий и тестировать адаптер.
7. **Воспроизводимость.** Фактический Android releaseRuntimeClasspath содержит
   Billing **8.0.0**, хотя документы говорят v7. Проверено Gradle dependencyInsight;
   это устаревшие документы, не обнаруженная просроченная библиотека. CI использует
   плавающий Flutter stable. Зафиксировать проверенную связку SDK/JDK/Flutter,
   версию Firebase CLI и требования JDK 21 к эмулятору; обновлять согласованно.
8. **Медиа.** В `D:/AI/out` обнаружены тестовая PNG, ambient WAV и один SFX.
   Это не полный согласованный набор «косметика + 3 SFX + loop» с manifest/checksums.
   Наличие WAV с именем loop не подтверждает бесшовность. Сначала завершить
   acceptance DEC-0019; расширение моделей сейчас не приоритет.
9. **Память проекта.** TASK утверждал «No product code changed yet» и «A4 needs
   owner», PLAN ссылался на 196 тестов и stage 0. README/status описывают старое
   состояние и монетизацию. Журнал закрывает A6 по нерепрезентативным тестам.
   Evidence блока протокола удостоверяет только protocol checks, не Firebase
   и не магазин. TASK исправлен этим аудитом; остальные документы требуют сверки.

## Оценка дальнейшего плана

Порядок **A → B → C → D** и отказ от общей доски сильны и соответствуют решениям.
Менять направление проекта не требуется; требуется строгое закрытие приёмки.

| Участок | Состояние на контрольной точке | Следующий критерий |
| --- | --- | --- |
| 0 | Ветки и планы сведены, статусные документы отстают | Синхронизировать README/статус/PLAN с кодом и DEC |
| A0/A1/A2/A8 | Основной код внесён; профильная проверка устройства заявлена | Чистая release-сборка, фактические DI-адаптеры, запуск |
| A3 | Mapping/merge внесены, live RC проверен | Тесты репозитория, persistent cache, offline и ошибки типов |
| A4 | Firebase интегрирован локально | Воспроизводимость в CI и сквозные release-сценарии |
| A5 | Не закрыт | Runtime principal, Play permissions, deployment и verified purchase |
| A6 | Повторно открыт аудитом | Настоящий payload проходит безопасные правила |
| A7 | Частично: панель есть | Mode gates, fatal/ANR, символы и события трёх режимов |
| B | План соответствует найденным дефектам | RNG → lifecycle/session → process death/UI; registry только как внешняя граница |
| C | Доход не доказан | Google link → один cosmetic SKU → verify → equip → reinstall/restore |
| D | Когорты ещё не основание для выбора победителя | Согласованные события и созревшие окна D7/D30 |

Оценки длительности в плане — рабочие гипотезы, не подтверждённая скорость.
«10–15 дней на QA и когорты» нельзя трактовать как готовый D30: он требует 30 дней
созревания соответствующей когорты. Включить экспорт данных до начала окна.
Blaze блокирует облачный deploy Functions, но не исправления F1–F7 и UI-тесты.

### Самые сильные векторы: рекомендуемые следующие пакеты работ

1. **Сохранение и выпускаемая сборка.** Закрыть F1/F2/F7, CI rules-тесты;
   получить чистый release APK и успешный cloud save/load настоящей модели.
   Это защищает пользовательский прогресс и устраняет зависимость от компьютера автора.
2. **Надёжная и измеримая игра.** Закрыть F3/F4/F5, затем B1/B3/B4:
   выключатели, единые события, RNG, round/session ID, повторный вход и process death.
   B2 не должен превращаться в общий движок; RU/EN и реальные UI-сценарии остаются в B.
3. **Одна законченная покупка.** После необходимых A/B-проверок провести ровно
   один cosmetic-сценарий C, включая восстановление аккаунта и покупки.
   Медиа использовать для этой конкретной продаваемой косметики.
4. **Глубина лучшего режима по данным.** В D сравнить активацию/повторные сессии/
   retention и покупки по режимам; после созревания когорт выбрать Tetris или Match-3
   для следующей инвестиции по DEC-0005. Пока победитель неизвестен. Для Match-3
   не применять classic/tetris early-gameover KPI к фиксированным 30 ходам.

Не расширять scope до четвёртого режима, Pass/валюты/колеса, RuStore или новых
семейств AI-моделей: действующие DEC уже задают более узкий первый выпуск.
