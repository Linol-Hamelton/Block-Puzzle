# Эмулятор и матрица устройств — конфигурация

Дата: 2026-09-14
Основание: [DEC-0014](../../.ai/DECISIONS.md) — физическое устройство одно
(личный Redmi владельца), остальное покрывается эмуляторами.
Железо разработчика (снято на машине 2026-09-14): Intel Core i9-13900HX,
24 ядра / 32 потока, 31.7 ГБ ОЗУ, NVIDIA RTX 4060 Laptop 8 ГБ, свободно
86 ГБ на `C:` и 447 ГБ на `D:`. Гипервизор в системе **уже запущен**
(включена VBS, обнаружен Hyper-V).

---

## 1. Главное ограничение, которое нельзя обойти конфигурацией

Целевые показатели — холодный старт p90 ≤ 2.5 с и 60 fps на Redmi 9/10,
то есть на слабом устройстве. Эмулятор на i9-13900HX с RTX 4060 **быстрее**
целевого телефона в разы. Из этого следует прямо:

> Эмулятор **не может** измерить гейт производительности. Никакая настройка
> не превращает его в низкобюджетный телефон: он не воспроизводит тепловой
> троттлинг, реальную стоимость GPU-операций, скорость флеш-памяти и вендорские
> оболочки (MIUI, One UI, Magic UI).

Поэтому роли разделены жёстко:

| Инструмент | Что им проверяется |
|---|---|
| **Эмулятор** | матрица экранов, плотностей и масштаба текста; уровни API; жизненный цикл (холодное убийство, сворачивание, восстановление); функциональный смоук трёх режимов; виджет- и интеграционные тесты в CI |
| **Redmi (единственный физический)** | холодный старт, кадровая частота, тепловое поведение, реальный ввод — перетаскивание в Classic, DAS/ARR в Tetris, свайп в Match-3 |
| **Когорта закрытого теста** | разнообразие вендоров и чипов; Play vitals, crash-free и ANR вместо матрицы QA |

Это и есть «ослабленный гейт» из DEC-0014. Указывать ослабление надо везде, где
показатель докладывается, иначе цифра будет выглядеть подтверждённой.

## 2. Выбор эмулятора: Android Studio AVD на WHPX

**Берём AVD из Android Studio, ускорение — WHPX.** Причина не в рейтингах, а в
состоянии конкретной машины: гипервизор уже запущен. Genymotion рекомендует
**отключать** Hyper-V на Windows, а отключение сломает и WSL2, и Docker, и саму
поддержку VBS. WHPX — прослойка, которая даёт эмулятору использовать уже
работающий Hyper-V, и это официально рекомендованный путь на Windows.

Intel HAXM не рассматривается: он несовместим с включённым Hyper-V и на
современных сборках Windows вытеснен WHPX.

Прочие варианты (BlueStacks, LDPlayer и подобные) — потребительские, не
инструменты разработчика: нет выбора уровня API, нет холодной загрузки, нет
надёжного `adb`-профилирования. Для QA не годятся.

### Что установить

Android SDK на машине **отсутствует** (`emulator.exe` не найден). Нужен
Android Studio либо командные инструменты SDK; заодно это закрывает отсутствие
Android-тулчейна, отмеченное ранее.

Установочные образы и AVD кладите на `D:`. **Одной переменной для этого мало:**
`ANDROID_SDK_ROOT` (или `ANDROID_HOME`) переносит сам SDK и системные образы, а
созданные AVD по умолчанию всё равно лягут в профиль на `C:`. Для них нужна
отдельная `ANDROID_AVD_HOME`. Задать обе до первой загрузки образов.

## 3. Набор AVD

Пять профилей. Каждый закрывает свой класс дефектов.

| AVD | Профиль | Образ | Что ловит |
|---|---|---|---|
| `small_720` | ~5", 720×1280, hdpi | Google APIs, API 36 | переполнение HUD, обрезание счёта и превью next/hold — самый урожайный профиль |
| `pixel_1080` | Pixel-класс, 1080×2400 | **Google Play**, API 36 | основной функциональный смоук; образ с Play Store нужен для песочницы покупок |
| `tall_ratio` | 1080×2640, высокое соотношение | Google APIs, API 36 | вёрстка при нестандартном соотношении, вырезы |
| `min_api` | Pixel-класс | Google APIs, **API 24** | реальный нижний уровень поддержки |
| `large_screen` | планшет ≥600dp | Google APIs, API 36 | функциональная проверка большого экрана (DEC-0020) |

Замечания к таблице:

1. **Образ с Google Play обязателен** для `pixel_1080`. Без Play Store на
   образе нельзя провести песочную покупку, а это гейт этапа A5.
2. **`minSdk` закреплён числом 24** по [DEC-0021](../../.ai/DECISIONS.md) —
   это фактическое значение Flutter (`minSdkVersionInt = 24`), которое раньше
   приезжало через `flutter.minSdkVersion` и ехало вместе с SDK.
3. **Планшетный профиль нужен, хотя приложение портретное.** Ранее здесь
   утверждалось обратное; это было неверно. В target SDK 36 изменено поведение
   для экранов от 600dp, а исключение действует для приложений, распознанных как
   игры — но его нужно заявить: в манифесте не было `android:appCategory="game"`.
   По [DEC-0020](../../.ai/DECISIONS.md) категория объявляется, и добавляется
   функциональный тест большого экрана. Проверять надо на артефакте, доставленном
   через Play, — локальная сборка этот контракт не закрывает.

## 4. Настройки производительности AVD

- **Ускорение:** WHPX (проверяется `emulator -accel-check`).
- **Ядра:** 4. Больше не даёт прироста и отбирает потоки у сборки Flutter.
- **ОЗУ:** 4096 МБ, VM heap 512 МБ. Из 31.7 ГБ это безопасно.
- **Графика:** Hardware — GLES 2.0. На ноутбуке с гибридной графикой убедиться,
  что эмулятор взял RTX 4060, а не Intel UHD: в панели NVIDIA задать дискретный
  адаптер для `emulator.exe` либо `qemu-system-x86_64.exe`.
- **Холодная загрузка** для проверок холодного старта и восстановления после
  убийства; быстрый снимок (Quick Boot) — для повседневной работы.
- **VBS** отнимает несколько процентов производительности виртуализации.
  Отключать её ради эмулятора не нужно: показатели всё равно снимаются на
  Redmi, а VBS — защита реальной рабочей машины.

## 5. Что проверять именно на эмуляторе

Прямо связано с пунктами утверждённого блока работ:

- **Завершение процесса — три разных сценария, не один.** Прежняя редакция
  предлагала `adb shell am kill` без имени пакета и `adb emu kill`; первое
  неполно, второе гасит эмулятор целиком и внезапную гибель приложения не
  воспроизводит. Проверять надо все три:

  | Сценарий | Команда | Что проверяется |
  |---|---|---|
  | смерть фонового процесса | `adb shell am kill <package>` | система убила свёрнутое приложение ради памяти |
  | принудительная остановка | `adb shell am force-stop <package>`, затем явный запуск | пользователь закрыл приложение из настроек |
  | внезапная гибель foreground | `adb shell run-as <package> kill -9 <pid>` на отладочной сборке | краш или OOM во время игры |

  Для каждого фиксировать: точку сохранения, допустимую потерю последних
  действий, восстановление RNG, счёта и режима, отсутствие дублирующихся
  `game_start`/`game_end`. **Данные приложения не очищать** — `pm clear`
  проверяет другое.
- **Совместное существование трёх сохранений** — требование DEC-0001: три
  приостановленные игры не должны затирать друг друга.
- **Kill-switch режимов** — требование DEC-0002: выключенный режим недоступен
  и по прямому маршруту, а не только скрыт с экрана.
- **Масштаб текста и мелкий экран** — увеличенный шрифт системы на `small_720`.
- **Уровень API** — прогон на `min_api` ловит несовместимости плагинов
  (`in_app_purchase`, Firebase) раньше, чем это сделает магазин.

## 6. Что снимать на Redmi и чем

На эмуляторе эти измерения бессмысленны:

```bash
# --dart-define обязателен: без него APP_ENV=dev и DI снова возьмёт
# debug-адаптеры, то есть измерять вы будете не то, что выйдет в релизе (DEC-0007)
flutter run --profile --dart-define=APP_ENV=prod --dart-define=APP_FLAVOR=release
flutter build apk --profile --dart-define=APP_ENV=prod --dart-define=APP_FLAVOR=release
```

Различать три величины и не смешивать их в одну «скорость запуска»: старт
Activity, первый отрисованный кадр и готовность игрового экрана к вводу.

Дальше — временная шкала в DevTools для кадров и `adb shell am start -W` для
холодного старта. Снятые значения помечать как **одна точка данных**, а не
покрытие матрицы, согласно DEC-0014.
